# Gu Game Remastered

A new Discord game, built from scratch. Shares nothing with the original
`Gu/GuGame` — no code, no data, no schema.

**Stack:** Python + discord.py, PostgreSQL, deployed on Railway.

---

## Database

The schema is defined by the `.sql` files in `db/migrations/`. They are the
source of truth — there is no ORM and nothing is autogenerated. You write the
DDL; the runner applies it once, in order, and records that it did.

### Rules

1. **Migrations are forward-only.** Once a file has been applied anywhere, it is
   frozen. Need a change? Write a new migration. The runner stores a checksum of
   every applied file and refuses to run if one was edited underneath it.
2. **Filenames are `NNNN_lower_snake_case.sql`.** The number is the version and
   sets the apply order. A file that does not match is a hard error, not a skip —
   a typo that silently never runs is the worst possible failure here.
3. **Each migration runs in its own transaction.** Postgres DDL is
   transactional, so a migration that fails part way leaves nothing behind, and
   the ones before it stay applied.

### Commands

```bash
python -m db.migrate status     # what is applied, what is pending
python -m db.migrate up         # apply everything pending
python -m db.migrate new <name> # scaffold the next numbered file
python -m db.migrate verify     # non-zero exit on drift or pending work (CI)

python -m db.lint               # parse every migration — needs no database
```

`db.lint` parses each migration with libpg_query, the actual PostgreSQL parser,
so a syntax error surfaces locally instead of half way through a deploy. It
checks grammar only — a reference to a column that does not exist still needs a
real `migrate up` to catch.

`up` runs automatically on every Railway deploy via the `release` line in
`Procfile`, and takes a Postgres advisory lock so two instances deploying at
once cannot both migrate.

### Schema conventions

These hold across every table. They are the deliberate corrections to how the
original game's database grew:

| Convention | Why |
|---|---|
| Surrogate `<thing>_id` primary keys | The Discord snowflake appears in exactly one column in the whole database, not copied into every child table as an unconstrained `BIGINT`. |
| `TIMESTAMPTZ`, never epoch integers | Postgres does the date arithmetic; `now()` is the default instead of something every caller computes. |
| Every FK declared, every FK indexed | Postgres indexes the referenced side automatically but never the referencing side — an unindexed FK makes the parent's delete scan. |
| `CASCADE` for dependent rows, `RESTRICT` for history | Losing a player should not quietly erase the audit trail of what was done to them. |
| `JSONB` only for open-ended payloads | Anything ever filtered, sorted, or summed gets a real column. |
| Features extend sideways, not wider | New systems add tables. `players` holds identity and is finished — this is what stops it becoming a 120-column table again. |

## Local setup

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env       # then fill it in

./tools/localpg.ps1 start  # start the local database
python -m db.migrate up
python -m pytest tests/    # 29 tests, all against a real Postgres
```

### The local database

A portable **PostgreSQL 17.11** lives in `../localpg` — outside this repo and
untracked. It is not a Windows service, needs no admin rights, and runs only
while started. Port **55432**, so it cannot collide with a real install; trust
auth on `127.0.0.1` only.

```powershell
./tools/localpg.ps1 start | stop | status | psql | log | reset
```

`reset` drops `gugame_dev`, recreates it and re-migrates from scratch — the
fastest way to prove the migrations still work from nothing.

To replace it, download PostgreSQL's zip-format Windows binaries, extract to
`../localpg/pgsql`, then `initdb -D ../localpg/data -U postgres -A trust`.

### Against Railway instead

Point `DATABASE_URL` at the **public** URL — Railway dashboard, Postgres service
→ Variables → `DATABASE_PUBLIC_URL`. The internal `DATABASE_URL` only resolves
from inside Railway's network.

> `tests/` writes to whatever `DATABASE_URL` names. Keep it on a scratch
> database.

## The Path system

Combat is built on the Path Attainment & Weakness design. Three tables carry it:

- **`paths`** — the 28 Path types. `combat` (21) use the matchup chart,
  `special` (Human, Heaven) sit in the chart with bespoke rules on top, and
  `exotic` (Qi, Dream, Painting, Food, Rule) opt out via `uses_matchups = false`
  because their value comes from unique mechanics.
- **`path_matchups`** — a directed attacker→defender chart, 108 rows. Both
  columns of the design chart read from the attacker's side, so the two
  directions of a pairing are independent facts: `fire→wood` being an advantage
  says nothing about `wood→fire`. **Neutral is an absent row**, which keeps this
  at 108 rows rather than 28×28 = 784.
- **`attainment_tiers`** — Uninitiated (0) through Supreme Grandmaster (10).
  `tier` is both the ordinal and the primary key, so "at least Grandmaster" is
  `tier >= 6`, an integer comparison rather than a name lookup.

Per-player state is **`player_path_attainment`**, one row per Path a player has
actually touched — a missing row means Uninitiated, so a new character starts
with zero rows rather than 28. In the old game this shape would have been 28
more columns on `players`; here, adding a Path is an `INSERT` into `paths`.

Balance numbers live in rows, not in Python: magnitudes in
`matchup_interactions`, scaling in `attainment_tiers`, and globals like the
+50% matchup cap in `game_config`. Retuning is an `UPDATE` in a new migration,
not a code change.

### Known gaps

- **Metal Path has no offensive matchups.** It appears only as a *defender* in
  the design chart (Lightning and Refinement beat it; it resists Sword), so
  Metal techniques are currently neutral into everything.
- **`insight_required` is entirely placeholder** — the design doc gives no
  curve. Currently ~2.5× per tier.
- **`resistance_bonus` above Grandmaster is placeholder.** Only the Grandmaster
  +10% is specified by the doc.

The chart and tier tables are generated by `tools/gen_path_seed.py`, which
validates them (no reflexive matchups, no duplicate pairs, no unknown Paths)
before writing the migration. Edit that script and re-run it to produce a *new*
migration — never to edit an applied one.

## Combat model

The player is the combatant. Battles are turn-based with **no switching**: the
loadout is committed before the fight and is your entire answer to whatever you
meet — which is what makes Path coverage a real decision rather than a footnote.

"Pokémon-like" here means the **type chart**, not creature collecting.

### Techniques

`techniques` holds definitions for both hand-authored content and player-created
killer moves — one table, distinguished by `created_by` (NULL = canonical).
Splitting them would turn every join in the damage pipeline into a union.

`technique_paths` carries the typing, one row per Path. Dual-Path moves like
Blazing Heaven Sword (Sword + Fire) get two rows, and `weight` implements the
spec's weighted formula — an even split reproduces the simple average, 0.70/0.30
gives the rare-move variant. **Weights must total exactly 1**, enforced by a
`DEFERRABLE INITIALLY DEFERRED` constraint trigger so it checks at COMMIT rather
than failing mid-insert when a 0.70/0.30 pair is legitimately still at 0.70.

`player_loadout` uses a composite FK into `player_techniques`, so equipping a
technique you don't know is impossible rather than merely validated, and
un-learning one clears the slot automatically.

### Weakness resolution

A technique of Path P hitting a creature resolves in this order:

1. **`creature_path_modifiers`** — an explicit per-species override. Wins.
2. **`path_matchups`** — derived, P against the creature's own Path.
3. **Neutral** — the absent-row default.

Both layers are necessary. The chart alone can't express the spec's own example
(the Nine Distortion Wolf resisting Sword and Earth is a fact about its hide,
not about its Path), and it has no way to express immunity at all. The
`creature_incoming_paths` view resolves the precedence once so combat and the
bestiary UI can't drift apart by implementing it differently. For dual-typed
creatures it takes the strongest single interaction rather than stacking —
stacking is how Pokémon reaches 4×, and the spec is explicit that even 2× is too
extreme alongside attainment, Dao Marks, equipment and crits.

### Discovery

`player_bestiary_paths` is a discovery log: a row means *this player knows how
that species reacts to that Path*. The interaction value is **never copied** —
it's read live from the species. That keeps rebalancing honest, since retuning a
creature updates every player's bestiary instead of leaving thousands of stale
snapshots. "Unknown Traits: 2" is a count difference, not a stored number.

`discovered_via` distinguishes learning it the hard way (`combat`) from deducing
it with Wisdom Path (`insight`, spec §7) from being told (`shared`).

## Cultivation & physique

The other two pillars. Both live in their own tables rather than as columns on
`players` — that separation is the rule that stops `players` growing back into
the 120-column table the original ended up with.

- **`realms`** — 9 ranks × 3 stages. `cultivation_required` is cumulative, so
  deriving a realm from a lifetime total is one indexed range scan, and
  technique gating is just `techniques.rank <= realms.rank`.
- **`player_cultivation`** — realm, cultivation total, essence/qi pools,
  aptitude. Caps come from the realm rather than being copied here, so a
  breakthrough takes effect the moment `realm_id` changes.
- **`physiques` / `player_physique`** — innate bodies and the body pillar's
  stat output. Equipment and buffs layer on at combat time; these columns are
  this pillar's contribution only, never a cached grand total.

### Training sessions

`training_sessions` backs `/cultivate path:strength duration:8h`. A session is a
*claim on a span of time*, resolved when the player returns — storing intent and
paying out later is what makes duration meaningful and keeps a disconnect from
costing anything.

`path_code IS NULL` means pure training: full XP, no insight. Set means the
focused trade — reduced XP (`path_cultivation_xp_rate` 0.85 /
`path_physique_xp_rate` 0.80) for insight and a Dao Mark chance.

Three constraints carry real weight here:

- A **partial unique index** on `(player_id) WHERE resolved_at IS NULL` allows
  only one active session. Without it, two racing commands both open a session
  and both pay out for the same wall-clock hours.
- Resolution is **all-or-nothing** — `resolved_at` and all three granted figures
  are present together or absent together. Half-resolved rows are what quietly
  double-pay.
- Insight **requires a Path**, so a pure session cannot grant any.

### Known gaps

- **The realm curve is entirely placeholder** — 1.9× per stage, 27 steps ending
  at ~9.3 billion cumulative. The design doc gives no curve.
- Physique stat multipliers are first-pass balance guesses.

## Battles & the damage pipeline

### Battle state

- **`battles`** — turn-based fights: `pve`, `duel` (`dungeon` reserved; its
  run/stage tables come later). `rng_seed` makes a disputed fight replayable.
  CHECKs keep status honest: active ⟺ no end time, and a winner requires a
  finished battle.
- **`battle_combatants`** — exactly one of `player_id`/`species_id` per row.
  `snapshot` freezes derived stats at battle start; combat reads the snapshot,
  never the live tables, so a duel result still explains itself after both
  players change builds. `RESTRICT` on players — battle history involves other
  people, same reasoning as the audit log.
- **`player_active_battle`** — the one-fight-at-a-time rule as a claim table;
  the primary key *is* the enforcement. World boss attacks take no claim.
- **`battle_actions`** — append-only log storing every resolved number
  (base, attainment, matchup, damage), so history survives rebalancing and a
  "why did that hit for 15,000?" is answered by reading the row.
  `technique_id` is `SET NULL` (player-created moves cascade away with their
  creator) but the name and numbers stay.
- **`world_boss_instances` / `world_boss_contributions`** — deliberately *not*
  battles: many players hitting one shared HP pool over hours is a different
  shape. One living instance per species (partial unique index); `defeated`
  requires HP exactly 0.

### The damage pipeline, in the database

The spec's damage flow is three SQL functions living next to the data they
read — one implementation serving the bot, ad-hoc psql balance queries, and the
tests, with no Python copy to drift:

- `technique_attainment_bonus(player, technique)` — weight-averaged tier bonus;
  missing attainment rows read as Uninitiated.
- `technique_matchup_modifier(technique, species)` — sums each Path's
  interaction from `creature_incoming_paths`, clamps to
  [`matchup_penalty_floor`, `matchup_bonus_cap`]. Returns exactly −1 (immune)
  only when *every* component Path is immune; one immune half of a dual-Path
  move feeds −1.0 into the sum where the floor catches it.
- `compute_technique_damage(player, technique, species, external, defense)` —
  the whole pipeline, returning every intermediate stage. `external` is the
  Dao Marks/equipment/buffs hook (pass 1 until those exist); defense is
  diminishing-returns (`defense_scale` = 100 defense halves damage), and a
  landed hit never rounds below 1 while zero-power and immune hits deal
  exactly 0.

The tests *are* the spec's worked examples: Blood Blade resolving to exactly
15,000, the 50/50 and 70/30 dual-Path formulas, the +50% cap holding, and the
full section-13 combat loop — attack, log, discover the weakness, read the
bestiary, count unknown traits — as one test.
